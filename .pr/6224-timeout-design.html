Bound zero-output LLM timeout retries

Issue #6224: a request that repeatedly reaches the 300-second deadline without output should not silently spend all five ordinary retry attempts.

Behavior

CaseBeforeAfter
Configured deadline, no outputAll num_retries attempts, normally fiveAt most hard_timeout_max_attempts, normally two; terminal LLMHardTimeoutError suggests a shorter or chunked response
LiteLLM transport reaches the same deadlineCould bypass the SDK timer and use all retriesCounts toward the same no-output attempt cap
Provider timeout before deadline, or timeout after streamed outputOrdinary retry policyOrdinary retry policy remains
Async stream idle timeoutPer-chunk idle deadlineStill uses the independent stream_idle_timeout setting

Retry boundary

Chat or Responses call→per-attempt SDK / LiteLLM deadline→record whether output appeared→Tenacity retry decision→typed error and classification

The no-output counter lives in the SDK retry decorator. A full-deadline LiteLLM timeout is normalized to the same internal timeout type as an SDK deadline. Retry logs include attempt number, total attempts, and elapsed time. A completed output chunk prevents the early-stop classification, including when a third-party async wrapper supplies a synchronous iterator.

Configuration and compatibility

LLM(
    model="openai/gpt-4o-mini",
    timeout=300,                 # existing per-attempt deadline, seconds
    num_retries=5,               # existing ordinary retry limit
    hard_timeout_max_attempts=2 # new per-profile no-output limit
)

The new field is additive, defaults to two, and is exported by the SDK settings schema. Existing timeout and event payloads remain loadable; no persisted-settings migration is needed. LLMHardTimeoutError subclasses LLMTimeoutError, so existing timeout handlers still catch it. The new classification avoids a futile retry hint after the cap.

Partial output preservation and stopping a blocked synchronous transport call are outside this change. The synchronous path counts a timeout when LiteLLM raises it.
